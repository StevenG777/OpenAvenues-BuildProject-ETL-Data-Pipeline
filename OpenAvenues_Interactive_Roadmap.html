Data Engineering Project Roadmap

Project: OpenAvenues-BuildProject-ETL-Data-Pipeline
Goal: Evolve the current Airflow + MongoDB pipeline into a configuration-driven, privacy-aware, multi-environment data provisioning platform.

Core problem: How can a company automatically provision realistic, smaller, privacy-protected copies of production-like data into development, testing, staging, and sandbox environments while maintaining data integrity?

1. Current project foundation

Your project is more than a generic ETL demo: it already has a staged copy → sanitize → minimize → publish design. This roadmap distinguishes improvements to the existing pipeline from new capabilities.

Security boundary: Any staging location that holds unsanitized production-like data must be treated as restricted. Do not put raw confidential data in ordinary development infrastructure before sanitization.

Shared capabilities: Run IDs, audit metrics, validation, least-privilege access, structured logging, and automated tests.

Phase 0 — Reliability before more complexity

Improvement Why needed High-level steps
Fail on unsuccessful writes (improve) Caught-and-printed batch exceptions can otherwise result in incomplete datasets and apparent success. Raise exceptions, record failed batches and verify counts before publication.
Safe staging and replacement (improve) Clearing or replacing a destination before successful completion risks losing the previous valid dataset. Write run-specific staging collections/tables, validate, then publish only on success.
Protect production data (improve) Checking only a particular database name is not a sufficient access-control boundary. Read-only source credentials, explicit environment classification, destination allowlists, network isolation.
Correct cross-database behavior (bug fix) Source data must never be dropped during a source-to-destination transform. Remove destructive source operations, add tests with different source/destination names.
Idempotency and retry safety (improve) Airflow retries can repeat operations. Add run IDs, retry-safe writes, failure cleanup, deduplication / safe cutover semantics.

Acceptance test: Interrupt a copy midway; previous valid published data remains available, Airflow marks the step failed, and a retry completes without duplicates.

Phase 1 — Advanced MongoDB sanitization and obfuscation

1.1 Nested field transformation engine (improve)

Why: Financial-data documents contain nested objects, arrays of objects, arrays of primitive values, and unpredictable dictionary keys. A top-level if field in doc lookup cannot match these.

Proposed custom YAML syntax:

collections:
  customers:
    email:
      strategy: redact
      params: {preset: mask_email}
    tier_and_details.*.benefits[*]:
      strategy: redact
      params: {preset: mask_all}
    accounts[*]:
      strategy: pseudonymize
  transactions:
    transactions[*].amount:
      strategy: perturb
      params: {noise_percent: 0.05}
    transactions[*].symbol:
      strategy: substitute
      params: {field_type: stock_symbol}

These are rules for your own path resolver, not native MongoDB query syntax: . navigates nested fields, * matches arbitrary object keys, and [*] iterates array elements.

Steps: Build the path resolver → match leaf values → apply mapped strategies → preserve the outer document → test mixed nested lists and dictionaries.

1.2 Deterministic pseudonymization (improve)

Why: Independently salted hashes of the same account_id break relationships between customers.accounts, accounts.account_id, and transactions.account_id.

Intended invariant: One original identifier maps to the same pseudonymous identifier across every collection in an environment (for example, 371138 → acct_X7 everywhere).

Steps: Add a keyed deterministic mapping (e.g., HMAC-SHA256 or a secure mapping store), apply it to all references, keep the secret out of code/YAML, and test joins after transformations. Ordinary unsalted hashing is unsafe for predictable identifiers.

1.3 Complete sanitization operation library (improve)

Why: field_removal and doc_removal currently act as placeholders in the shared code.

Steps: Define separate contracts for value replacement, field deletion and document exclusion; implement nullification, date shifting and masking; expose strategies through maps_functions.py; test edge cases.

1.4 BSON type awareness (new)

Why: datetime, Boolean fields, numeric account IDs, and MongoDB Decimal128 require different handling. A text redaction strategy must not silently corrupt field types.

Steps: Validate accepted input/output types per strategy, support native BSON values, reject incompatible operations, and document intentional type changes.

Phase 2 — Smarter minimization and data quality

2.1 Relationship-aware sampling (improve)

Why: Sampling customers, accounts and transactions independently may create dangling references.

Steps: Select root customers → collect referenced account IDs → select those accounts → collect related transaction documents → cap transaction volume if necessary → validate referential integrity.

Provide both independent random sampling and relationship-preserving sampling modes.

2.2 Nested array minimization (new)

Why: An individual transactions document contains a long array of entries, even when top-level document counts are small.

Steps: Implement array limit, sample and date_window rules through the nested-path engine; recompute derived fields like transaction_count when required by their meaning.

2.3 Privacy and data quality gates (new)

Check Example
Structural All required account fields are present.
Type Date fields remain dates, expected numeric fields remain numeric.
Relationships Retained customer/account/transaction references resolve.
Privacy Sensitive fields have the configured approved transforms.
Volume Dataset satisfies row and byte limits.
Completeness Expected collections processed without skipped failures.

Steps: Validate configs with Pydantic; add dataset assertions and privacy tests; create an Airflow validation TaskGroup that must pass before publication. Schema validation does not, on its own, prove privacy safety.

2.4 Schema profiling and sanitization coverage (new)

Why: Sensitive fields may be added to MongoDB collections without a matching YAML rule.

Steps: Profile schema paths and types, identify potential sensitive fields, compare them against policy coverage, and report uncovered paths without logging sensitive raw values.

Phase 3 — Airflow automation and engineering practices

Feature Why needed High-level steps
Automated data refresh (new) Development data becomes outdated. Schedule refresh, compare full vs incremental refresh, use watermarks and concurrency controls.
Observability / audit logging (new) Operators need counts, timings and failure details. Structured logs, run IDs, metrics for copied/transformed/rejected/published rows, alerts.
Automated testing and CI/CD (improve) New strategies can silently introduce regressions. Unit and integration tests, DAG import tests, GitHub Actions lint/test/config checks.
Config validation (improve) Invalid YAML must fail before accessing data. Pydantic models for source/destination, percentages, nested path syntax and strategies.
Environment security (improve) Online deployment requires production-grade isolation. Secrets outside Git, authenticated MongoDB, TLS, least-privilege credentials, private network.

Proposed execution stages: Copy → Sanitize/Obfuscate → Minimize → Validate → Publish → Generate Report → Clean up restricted staging.

Phase 4 — PostgreSQL and reusable database design

4.1 PostgreSQL-to-PostgreSQL provisioning (new)

Why: SQL adds normalized schemas, transactions, foreign-key constraints and migrations.

Illustrative modeling:

MongoDB PostgreSQL
customers customers, customer_accounts, customer_tiers
accounts accounts, account_products
transactions transaction_buckets, transaction_entries

Steps: Design relational schema, load equivalent finance-domain records, implement extraction and transformations using psycopg or SQLAlchemy, preserve referential integrity during pseudonymization/sampling, and run SQL checks.

Keep Airflow's metadata PostgreSQL independent of business-data PostgreSQL.

4.2 Database adapter interfaces (new)

Why: Shared configuration and orchestration should not imply identical MongoDB and SQL access code.

Steps: Define read, batch write, staging, publish and validation interfaces; implement MongoDB and PostgreSQL adapters; reuse business rules but isolate database-specific operations.

Phase 5 — Cloud deployment and optional extensions

Feature Why needed High-level steps
Cloud hosting (new) Demonstrate an always-accessible working system. Container deployment and/or managed databases, secure networking, credentials and persistence.
Infrastructure as code (new) Reproducible environments. Model networks, compute, secrets and data services in Terraform or equivalent.
Warehouse and analytics (optional) Show downstream analytical use cases. Export suitable transformed data into analytic tables and dashboard summaries.
Kubernetes (optional) Practice cluster operations and scaling. Only after simple cloud deployment works: Helm, secrets, storage, worker scaling.

Do not expose an unmodified local-development Airflow Compose stack directly to the public internet. Kubernetes is a stretch goal, not the immediate bottleneck.

6. Measurable acceptance criteria

Metric Example standard
Transformation coverage All configured sensitive paths handled or flagged.
Referential integrity No dangling references in the published subset.
Failure behavior Failed operations fail the Airflow run; existing target preserved.
Idempotency Rerunning does not duplicate published records.
Dataset reduction Row/byte budget achieved or exception reported.
BSON type handling Fields required to retain their types pass validation.
Reproducibility A new developer can deploy locally from documented instructions.

7. Recommended immediate priorities

  1. Safety and fail-fast behavior: preserve valid target data across partial failures.
  2. Nested transformations and consistent ID mapping: sanitize complex MongoDB structures without breaking relationships.
  3. Relationship-aware minimization and validation: generate a small, useful, test-ready subset.

After those succeed, PostgreSQL will extend a reliable common framework rather than duplicate a prototype.
